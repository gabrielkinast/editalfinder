# M2.3c — Frozen structured-input oracle and coverage

## Scope and provenance

This is offline composition verification beginning with already structured source records,
explicit assertions and evidence, not extraction from text/web/PDF. No network, persistence,
SQL changes, authenticated review, promotion, automatic association or merge is implemented.

Primary manual oracle: `tests/fixtures/m23c_v1.json`, version
`m2.3c-synthetic-structured-v1`. Operational oracle:
`tests/fixtures/m23c_operational_v1.json`, version `m2.3c-operational-v1`.
No expected values were captured from `integrate` or a normalizer. Expectations were selected
from the contracts below before running the scenarios. JSON lists are test projections of
existing DTO fields, not an additional production domain schema.

The first manifest contains 26 stable case IDs and 37 ordered candidate slots. Each case owns
its synthetic records; each candidate has an explicit `/records/<index>` DocumentUnit. IDs
are deterministic within a case; a case ID plus candidate index is the dataset-level key.
The existing `m23_fixtures.adapt_records` constructs RawSnapshot, FieldAssertion, Evidence,
IdentityEvidence, explicit claims, namespace and cycle. The new `m23c_fixtures.build` adds
only declared date typing, URL comparison policies, comparisons and named adversarial input
variants. It does not infer semantics from prose or turn raw records into extracted facts.

All scalars receive pointers into the source record and explicit roles; source/execution/
snapshot/candidate UUIDs are bound by the existing adapter. Every invocation decodes fresh
JSON so mutation cannot leak between tests. Collection evidence intentionally remains valid
for M2 while M1 may report `evidence_role_mismatch` for its narrower direct-field contract.
That is a limitation of composition, not a reason to weaken M1 or project M2 into it.

The historical case explicitly declares `typed_date_fields=["submission_deadline"]`:
M1 gets a `date`, not an ISO string guessed from a field name. The reference date is always
2026-07-01; collection-only M2 deadlines never silently set M1 availability.

`expected_identity_behavior`. Each candidate declares all seven expected-outcome sections

and exact error code. `near`/`over` search only the admission estimator for adjacent bounded

share one snapshot. Search is bounded to 100,000 padding characters per source record.
This deliberately exercises the real unchanged 64 MiB boundary rather than monkeypatching it.

Hybrid components preserve non-repayable and repayable expressions separately. Only a grant
ceiling is represented by `proposal_maximum`; the credit component stays `credit_principal`
as original M1 assertion. There is NO approved instrument identifier relating that amount to
a particular taxonomy claim. Calling both amounts normalized would be incorrect. Two
independent components cannot be declared contradictory merely from their coexistence.
The same-expression reverse financial range is the only existing supported definite
contradiction here. Explicit incompatibility between claims about the same named instrument
cannot yet be established with a typed instrument relationship; it remains a future decision.

## Corrections to the test harness, not to production

Initial executions caught an incorrect uniform `.input.context` assumption (organizations
uses `.context`) and the required URL normalization policy. These were harness errors, not
RED evidence for missing production behavior. An equivalent-URL test initially included an
extra fragment; url_identity.py explicitly preserves fragments. The input was corrected to
vary host case/default port only; its expected codes were not weakened.

A cross-record organization test initially expected lexical names to disappear. M22B's
approved contract explicitly preserves lexical presentation but suppresses comparison keys
and emits organization_evidence_invalid. The corrected test asserts both refusal artifacts
and lexical preservation, rather than changing approved production behavior.

This milestone adds characterization/regression tests for existing behavior, not new runtime
features. It therefore makes no claim of a production RED→GREEN implementation cycle.
Oracle mutation controls prove meaningful failures for changed expected diagnostics and
roles. No production change was necessary, and no synthetic RED stub or fake missing API
was introduced. No existing assertions, tests or review documents were removed or modified.
